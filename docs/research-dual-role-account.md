# 調査メモ：1つのアカウントで「農家」と「飲食店」の両方を使う（兼用アカウント）

作成日：2026年10月19日／状態：**調査のみ（実装していない）**

同じ人が農業と飲食店の両方を営み、販売と仕入れの両方を使う場合の調査です。採用は未決定のため、コードやデータは変更していません。既存アカウントの統合も実行していません。「同じメールでパスワードだけ違う2アカウント」を作る方式は、採用しない前提で調べています。

## 1. いまの認証の仕組み

- **ログイン**：Better Auth のメールアドレス＋パスワードでログインします（`src/lib/auth.ts`）。
- **立場の決め方**：登録時に `role`（`RESTAURANT` か `FARMER`）を1つ選びます。
  - 登録後に変えようとすると、`/update-user` へのリクエストを拒否します（`hooks.before`）。
- **画面の振り分け**：`getCurrentUser()`（`src/lib/session.ts`）が、セッションから `id・name・role` を取り出します。
  - `requireUser(role)`・`requireFarmer()`・`requireRestaurant()`（`src/lib/guard.ts`）がこの `role` を見て判断します。

## 2. データの構造

| 表 | 主な項目 | 関係 |
|---|---|---|
| `user` | `email`（一意）、`role`（1つだけ）、`onboardedAt` | 1人1行 |
| `account` | パスワードのハッシュ | `user` に属する |
| `FarmerProfile` | `userId`（**一意**） | `user` と 1対1 |
| `RestaurantProfile` | `userId`（**一意**） | `user` と 1対1 |
| `Listing`／`CostMemo`／`Review`（受けた側） | `farmerId` | 農園プロフィールにつながる |
| `Order`／`ListingInquiry`／`Review`（書いた側） | `restaurantId`・`farmerId` | 店・農園プロフィールにつながる |

**分かったこと**
- DB上、1人の `user` に農園プロフィールと店舗プロフィールの**両方を持たせること自体はすでに可能**です。どちらも `userId` は一意ですが、別々の表だからです。
- 両方を持てないようにしているのは、`user.role` が1つしかないことと、画面・権限確認がその `role` で分かれていることです。

## 3. 出品・注文・メッセージの権限確認

- **画面の入口**：ロールで確認します（`requireUser("FARMER")` など）。
- **出品・注文・記録の操作**：ドメイン処理（`src/lib/domain/*.ts`）で当事者を確認します。
  - 対象の「農園プロフィールの `userId`」または「店舗プロフィールの `userId`」が操作する本人かを見ています（例：`approveOrder` は `order.farmer.userId === farmerUserId`）。
  - ロールではなく**プロフィールの持ち主**で判断しているので、兼用にしても大きな作り直しは不要です。
- **ユーザーIDで記録している項目**（操作した人の記録）：
  - 注文の相談・出品の相談：`OrderMessage.senderId`、`InquiryMessage.senderId`
  - 状態の履歴・記録の訂正：`OrderEvent.actorId`、`RecordCorrection.actorId`
  - 支払い・受け渡しの記録：`PaymentRecord.confirmedBy`、`FulfillmentRecord.farmerSentBy`／`buyerReceivedBy`
  - 要相談の目印・レビューの通報：`needsDiscussionBy`、`ReviewReport.reporterId`
  - 表示の名前は、`senderId` が「その注文の農家側か店側か」で決めています。兼用の人が自分と取引すると区別できなくなるため、次の 4-②（自分の出品への申し込みを防ぐ）が前提になります。

## 4. 1アカウントに両方の役割を追加して切り替える場合の変更範囲（案）

1. **DB**：`user.role`（1つ）をやめ、「持っている役割の一覧」と「いま使っている役割」に分けます。
   - 「いま使っている役割」はセッションか、利用者ごとの設定として保存します。
   - 既存の `role` を初期値として移すマイグレーションが必要です（追加→移行→旧列の扱いを決める、の3段階）。
2. **認証・権限**：
   - `getCurrentUser()` が「いまの役割」を返すようにします。
   - `requireUser(role)` は「その役割を持っているか」も確認します。
   - 役割を追加する画面と、サーバー側の操作が必要です（今は登録後の変更を拒否しているので、そのルールの変更も必要）。
3. **自分の出品への申し込み防止**：
   - `createOrder` と `openInquiry` に「出品の農家の `userId` ≠ 申し込む店の `userId`」の確認を足します。
   - 検索結果からも自分の出品を外します。
   - サーバー側の確認が必須で、画面だけでは不十分です。
4. **画面**：
   - 上部・下部メニュー、ホーム、使い方案内は、今は役割ごとに分かれています。
   - これらを「いまの役割」で出し分け、切り替えボタン（例：マイページに「農家として使う／店として使う」）を置きます。
   - 下部メニューのバッジは、いまの役割の件数だけにするか、もう一方の件数も小さく出すかを決める必要があります。
5. **通知**：外部通知（メール等）は初期版の範囲外で、ありません。ホームの「今やること」の件数を、役割ごとに分けて出すだけで済みます。
6. **使い方案内**：役割ごとに初回表示を記録する必要があります（今は `onboardedAt` が1つだけ）。

## 5. 既存のアカウント・出品・注文を残したまま変更できるか

- **残せます**：既存のアカウント・出品・注文は、そのままで変更できます。
  - 出品・注文・レビューは、ユーザーではなく**プロフィールのID**につながっています。
  - 既存の1役割アカウントは、「役割が1つだけの兼用アカウント」としてそのまま使えます。

## 6. 既存の別アカウントを統合する機能は必要か（調査のみ・実行しない）

すでに「農家用」と「店用」の2つのアカウントを持っている人を1つにまとめる場合に必要なことです。

- **メールアドレス**：一意なので、どちらのメールとパスワードを残すかを本人に決めてもらう必要があります。
- **プロフィールの付け替え**：残さない側のプロフィールの `userId` を、残す側のユーザーに付け替えます。出品・注文はプロフィールにつながっているので、そのまま引き継げます。
- **ユーザーIDで記録した履歴の書き換え**：上の 3. の `senderId`・`actorId`・`confirmedBy` などを書き換える必要があります。
  - これは過去の記録の書き換えになるため、CLAUDE.md の「履歴を残す」方針との整合を、メンターと確認する必要があります。
  - 書き換えずに「統合前の別アカウントID」として残す方法もあります。
- **本人確認**：両方のアカウントにログインできる本人であることを、統合の前に確認する必要があります。
- **結論**：統合は手作業の移行作業になり、誤りがあると取引履歴に影響します。
  - 兼用を採用する場合も、まずは「新しく登録する人だけが役割を追加できる」形から始めるのが安全です。
  - 既存の2アカウントは、当面は別々のまま使う運用をおすすめします。
